## القرار التقني

- إبقاء Android بلغة Java، واستهداف Java 17 بدل Java 11.
- تشغيل Gradle باستخدام JDK 21. إصدار JVM الذي يشغّل Gradle مختلف عن إصدار كود التطبيق.
- فصل منطق الأموال في `core` يستهدف Java 17، ليُستخدم لاحقًا من backend يعمل بـJava 21.
- بدء backend بخدمة واحدة ذات حدود داخلية واضحة: معاملات، ميزانيات، وهوية مستخدم. فصل الخدمات يأتي عندما توجد حاجة قابلة للشرح والقياس.
- هذا الاتجاه يحل محل اقتراح الترحيل إلى Kotlin في خطة المراجعة السابقة، استجابةً لاختيار Java ومسار التدريب المستهدف.

## المرحلة الأولى: الأساس الحالي

أُضيف إلى الكود:

- استهداف Java 17 في Android، و`--release 17` في وحدة `core`.
- تثبيت إصدار Gradle JVM على 21 بدل 25.
- محلل مبالغ مشترك للمعاملات والميزانيات، بأخطاء مصنفة، وبدون rounding صامت.
- حسابات شهرية مستقلة عن Android وحدود الشهر والسنة، وتجميع لا يفيض عند تجاوز مجموع القيم سعة `long`.
- 36 اختبارًا للحسابات والمدخلات وحدود الأرقام والتواريخ والسنة الكبيسة.
- ملف CI لبناء APK وتشغيل اختبارات المجال وLint؛ نجاح التشغيل المستضاف يحتاج رفع المشروع وتشغيل GitHub Actions.

هذا فصل جزئي للمنطق وليس تطبيقًا كاملًا لـDDD أو TDD. لا يكفي وجود الاختبارات للادعاء أن جميع الميزات طُورت بدورة TDD.

## المرحلة الثانية: API حقيقية بـJava 21 وPostgreSQL

**المخرج:** خدمة مستقلة، متصلة بقاعدة PostgreSQL، مع عقد OpenAPI وأوامر تشغيل قابلة للتكرار.

1. API لإضافة وقراءة وتعديل وحذف المعاملات، وميزانيات وملخص شهري؛ pagination وحدود للمدخلات وأخطاء HTTP واضحة.
2. استخدام SparkJava إذا بقي مناسبًا ومدعومًا عند التنفيذ؛ راجع توافق واعتماديات الأمان أولًا، ووثّق البديل إن استلزم الأمر.
3. PostgreSQL مع migrations، ومبالغ minor units وcurrency معلنة، وقيود CHECK وفهارس حسب المستخدم والتاريخ.
4. jOOQ مع توليد الأنواع من schema؛ عدم إنشاء SQL بضم نصوص مدخلات المستخدم.
5. مصادقة عبر مزوّد OIDC موثوق؛ تحديد المستخدم من الهوية المتحققة على الخادم، وتفويض كل عملية على بياناته.
6. مفتاح idempotency لإنشاء معاملة: يُخزّن ضمن نفس معاملة قاعدة البيانات، ومقيّد بالمستخدم، مع بصمة الطلب. إعادة الطلب تُرجع النتيجة الأصلية؛ تغيّر الجسم مع نفس المفتاح يسبب conflict.
7. version/optimistic locking للتعديلات لمنع الكتابة فوق تعديل متزامن.

**دليل الاكتمال:** اختبارات PostgreSQL حقيقية تثبت عزل مستخدمين، منع التكرار عند التزامن وإعادة المحاولة، تعارض التعديل، rollback عند الفشل، وصحة الاستعلامات الشهرية. لا تستخدم H2 كدليل وحيد على سلوك PostgreSQL.

## المرحلة الثالثة: Spock وTDD وجودة التسليم

- احتفظ باختبارات JUnit الحالية، وأضف Spock لمواصفات backend واختبارات data-driven.
- طبّق دورة اختبار يفشل لسبب صحيح، ثم تنفيذ ينجحه، ثم refactor على ميزة جديدة، مثل idempotency. احفظ الدليل في سجل commits حقيقي.
- استخدم PostgreSQL عبر Testcontainers أو خدمة CI، واجعل اختبارات التكامل جزءًا صريحًا من الفحص المطلوب.
- اختبر ترحيلات Room ودوران الشاشة وإعادة الإنشاء أثناء الحفظ، وافصل ViewModel وRepository عن Activities.
- أضف فحوص الاعتماديات والأسرار والتنسيق. اعرض نتائج فعلية؛ لا تضف badges نجاح قبل وجود تشغيل ناجح.

## المرحلة الرابعة: Docker وRedis والمزامنة

- Dockerfile متعدد المراحل للخدمة وتشغيل كمستخدم غير root، وCompose لبيئة التطوير مع PostgreSQL وhealth checks وأسرار خارج Git.
- استمر في العمل محليًا دون شبكة. أضف outbox ومعرفات ثابتة وإعادة محاولة مع backoff وسياسة تعارض معلنة.
- استخدم Redis فقط لحالة مفيدة: rate limiting أو cache لملخص يمكن إعادة حسابه. لا تجعله المصدر الوحيد للبيانات أو ضمان منع التكرار.
- اختبر فقد الاتصال، سقوط Redis، ضياع استجابة نجاح الخادم، وانقطاع الخدمة بين حفظ البيانات وإرسال الرد.

**دليل الاكتمال:** سيناريو قابل للتشغيل يعيد إرسال طلب نجح سابقًا دون إنشاء معاملة ثانية، مع استمرار صحة البيانات عند توقف cache.

## المرحلة الخامسة: GCP وKubernetes والتشغيل

- بعد اكتمال الخدمة واختبارات التكامل، أضف manifests لـKubernetes: requests/limits وreadiness/liveness والإغلاق المنظم. لا تضع أسرارًا حقيقية داخل YAML.
- تحقق محليًا على kind أو بيئة مماثلة، ثم وثّق نشر GKE اختياريًا؛ إنشاء موارد مدفوعة يحتاج قرارًا منفصلًا بميزانية واضحة.
- استخدم قاعدة مُدارة وصلاحيات دنيا ومقاييس وسجلات منقحة. اختبر النسخ الاحتياطي والاستعادة.
- قس p50/p95 ونسبة الأخطاء ضمن حمل وحجم بيانات وبيئة معلنة. لا تنشر أرقام أداء أو ادعاءات high scale دون قياس.

## ماذا تعرض في البورتفوليو؟

- فيديو قصير يشرح مشكلة المستخدم ويعرض سيناريو كاملًا من Android إلى API، عندما يُنفّذ الربط.
- رسم معماري، قرارات ADR قصيرة، عقد API، تعليمات تشغيل، ونتائج اختبارات حقيقية.
- تجربة تزامن/إعادة محاولة توضح فائدة idempotency، وتقرير أداء قابل للتكرار.
- سيرة تصف ما أنجزته فعلًا. لا تذكر Redis أوKubernetes أوGCP كخبرة مكتسبة من المشروع قبل تشغيلها والتحقق منها.
- تدريب مستقل على هياكل البيانات والخوارزميات وSQL وHTTP والخيوط والتزامن، مع شرح القرارات بالإنجليزية. هذا لا يتحقق بمجرد إضافة dependency.
